# PR リスク評価（規約）

| 項目 | 内容 |
|---|---|
| 種別 | 規約（日付なしの生きた文書。変える場合は PR で） |
| 正本 | ai-team（開発体制のハブ）。このファイルは `scripts/bootstrap-repo.js --public` が置いた写しで、判定の基準は全リポジトリ共通。このリポジトリ固有の例は「付録」に書く。共通の基準を変えるときは ai-team 側に Issue を立てる |
| 使う場所 | `.github/pull_request_template.md`「影響範囲・リスク」、`/create-pr` の手順 4、このリポジトリの `AGENTS.md` から参照 |

PR ごとに、変更量ではなく「問題が起きたときのユーザー・本番・データ・金銭・セキュリティへの影響」で 🔴 高 / 🟡 中 / 🟢 低 を判定し、PR 本文の「影響範囲・リスク」に理由付きで書く。複数の要因があれば最も高いレベルを採用する。評価は「その PR が意図した経路で反映された状態」を対象にする（Web は公開後、アプリはストア公開後、運用スクリプトは live 実行時）。発生確率ではなく、現実的に起こりうる最悪の影響で判定する。

## 判定の観点

| 観点 | 確認するもの |
|---|---|
| 反映経路 | merge が即公開か、ストア審査を挟むか、手動デプロイか。cron・バックグラウンド処理はどこで動くか |
| 影響範囲 | 単一画面・単一ページか、全アプリ・全サイトか、生成物が数百件か、複数リポジトリに波及するか |
| 永続データ | ローカル DB、リモート DB、ブラウザの保存領域、端末の設定、配信データの版、正本の JSON |
| 金銭・権利 | 購入、consume、Entitlement、無料枠、価格、返金 |
| セキュリティ・秘密 | 認証、決済、署名、外部 URL、secrets、権限 |
| 外部サービス・自動処理 | 外部 API への書き込み、CI の cron と bot commit、配信基盤、ストア、広告、計測、通知、監視 |
| 生成物・検索流入 | 正本と再生成範囲、canonical / robots / noindex / sitemap、構造化データ |
| 復旧・検知 | revert で戻るか、データ復元が要るか、配信済み端末に残るか、ログ・preview・実機で検知できるか |

## レベル

### 🔴 高 — 次のいずれか 1 つでも該当（該当箇所を `path:line` で示せること）

- DB・ブラウザの保存領域・端末の設定の schema・移行・全件置換・削除・復元
- 認証、課金、Entitlement、consume、返金、secrets、権限、外部入力の検証
- 外部サービスへの投稿・更新、**main / 本番へ直接 commit・push する bot 経路**といった、外部または本番へ不可逆な書き込みを行う経路（dry-run・承認・冪等性のガードを弱める変更を含む）。Dependabot のように branch + PR を作るだけの bot は含まない（閉じれば戻る）
- APK / AAB / IPA の公開、production 設定、Manifest 権限、署名・配布設定
- 全サイトの canonical / robots / noindex、共通 middleware、数百ページの再生成を伴うジェネレータ変更
- 障害後に revert だけでは元のデータ・端末・外部状態を戻せない変更

### 🟡 中 — 本番で動くものを変える場合の既定値

- 本番で使うロジック、API 通信、状態管理、共通処理の変更
- 一部ユーザー・画面・ページ群に影響する生成処理やデータ変更（配信データの更新を含む）
- 外部 API の読取、リトライ、キャッシュ、通知、予約、バックグラウンド処理
- 計測、広告、Remote Config など運用・計測に影響する変更
- hooks、CI、Skill、AGENTS.md など AI と開発フローのガードを変える変更（「文書だから低」にしない）

### 🟢 低 — 次をすべて満たすときだけ

- 外部書き込み、永続データ、認証、課金、権限、自動実行に影響しない
- 影響が単一箇所に限定される
- 正本と生成物の関係を壊さない
- revert または再デプロイだけで復旧できる

例: 通常の文言・コメント、公開されない文書、局所的な装飾、既存の検証を弱めないテスト追加。

## 判定手順

1. `git diff main...HEAD` で差分を確認し、生成物なら正本の箇所を特定する
2. 変更箇所の入口・呼び出し元・書き込み先を grep で確認する（静的サイトなら読み込んでいる HTML、ジェネレータなら出力先、Flutter なら画面と Provider、スクリプトなら起動経路）
3. **触った機能の種類が下の「攻撃面」の表にあるか見る。** あれば「最低限確かめること」を当て、結果を PR 本文の「影響範囲・リスク」の「攻撃面」に書く。表に無い種類の機能なら、**このリポジトリでは行を足さず**、正本（ai-team）に Issue を立てて別 PR で足し、この PR 本文には気づいた内容だけ書く（1 branch = 1 Issue = 1 責務）
4. 観点表を上から当て、反映経路・自動実行・永続データ・外部サービス・復旧方法を確認する
5. 高のトリガーを先に判定し、該当しなければ中、次に低の成立条件をすべて確認する
6. 確認できることを未調査のまま推測しない。確認したうえで重大事項が不明なら「要確認」と書き、暫定的に一段上げて PR は Draft にする

履歴書き換え・force push・remote / 権限設定の変更・`--no-verify` はリスク評価の対象ではなく常に禁止（人間に依頼する）。

## 攻撃面（機能の種類ごと）

**リスクの高さ（上の表）とは別軸で、「この機能はどう攻撃されうるか」を引くための表。** 新しい機能を作るときと、既存の機能を触るときの両方で当てる。ここに無い種類の機能を作ったら、正本（ai-team）に Issue を立てて行を足す。

「最低限確かめること」は気づくための最小限で、詳しい確かめ方は「詳細」の資料にある。判定基準はこのリポジトリの `AGENTS.md`「Code Review Rules」が正本。

| 機能の種類 | 主な攻撃 | 最低限確かめること | 詳細 |
|---|---|---|---|
| 外部 URL をサーバー側で取得する | SSRF（内部サービス・クラウドのメタデータへ到達）、DNS rebinding、redirect による検証の迂回、巨大・圧縮レスポンスでの枯渇、取得した文章による Prompt Injection | 取得先のホストがユーザー入力で変わるか。変わるなら、DNS 解決後の IP を見ているか、redirect のたびに再検証しているか | ai-team の内部資料（URL 取得のセキュリティ） |
| ユーザー入力を保存して別の画面に出す | XSS、HTML インジェクション、保存時と表示時のエスケープの二重・欠落 | どこでエスケープしているか（保存時か表示時か）を 1 か所に決めているか。`innerHTML` / `dangerouslySetInnerHTML` / Flutter の `Html` 相当を grep したか | — |
| 課金・権利付与 | 消耗型が消費されず二度と買えなくなる、権利の二重付与、失敗時に権利が付く・消える | 消費の呼び出しが経路上にあるか。権利判定の失敗時・不明時の既定値 | `~/.claude/agents/security-reviewer.md` |
| 認証・セッション | セッションの固定化・失効漏れ、Cookie 属性の欠落、権限昇格 | 発行・検証・失効の 3 つが揃っているか。`httpOnly` / `secure` / `sameSite` と有効期限 | `~/.claude/agents/security-reviewer.md` |
| AI に外部の文章を渡す / AI が URL・画像を生成する | 取得した文章に仕込まれた指示で AI が動く、AI が生成した外部画像 URL 経由で入力内容が外部へ出る、AI が危険なリンクを出す | 外部由来の文章を指示として扱っていないか（データとして囲っているか）。AI が出した URL をそのまま取得・表示していないか | ai-team の内部資料（URL 取得のセキュリティ）の 6 章 |
| ファイルのアップロードと配信 | 拡張子と中身の不一致、パストラバーサル、配信時の Content-Type による実行 | 保存先のパスを入力から組み立てていないか。配信時の `Content-Type` と `Content-Disposition` | — |
| 全サイトに効く設定（`_headers` `_redirects` `robots.txt` `wrangler.toml`） | 1 ファイルの変更が全サイトに波及、noindex や robots の事故で検索から落ちる | 適用範囲のパターンが意図した範囲を超えていないか。外す方向の差分は広げる方向より厳しく見る | `~/.claude/agents/security-reviewer.md` |
| 広告 SDK・アフィリエイトリンク | 個人データの送信、リンクの改ざん・なりすまし、同意の欠落 | SDK に渡している値。リンクの生成元が正本のデータか | — |
| ネイティブの権限・署名 | 使っていない権限の増加、`exported` の付いたコンポーネント、署名鍵の混入 | 増えた権限を使うコードが同じ差分にあるか。鍵・パスワードがリポジトリに入っていないか | `~/.claude/agents/security-reviewer.md` |
| DB スキーマの移行 | 既存行が壊れる、版を戻してから上げ直す経路で開けなくなる、revert で戻らない | 移行が冪等か（既にある列・テーブルに当たっても落ちないか）。`DEFAULT` / `NOT NULL` を足したときの既存行 | — |

## PR への記載（テンプレート「影響範囲・リスク」）

| 項目 | 内容 |
|---|---|
| リスクレベル | 🔴 高 / 🟡 中 / 🟢 低（要確認なら明記） |
| 最悪の現実的な失敗 | 誰が・何を・どう困るか |
| 根拠（差分） | `path:line` |
| 入口・呼び出し元 | `path:line` |
| 永続データ・外部作用 | なし / あり（内容） |
| 攻撃面 | 該当なし / 該当行（上の「攻撃面（機能の種類ごと）」の機能の種類）と、当てた結果（判定手順 3） |
| 復旧 | revert で戻る / 再デプロイが要る / 戻らない（理由） |
| 未確認 | なし / あり（内容） |
| このレベルにした理由 | 一段上・一段下でない理由を 1〜2 行 |

禁止: 「影響なし」「問題なし」だけの記載、テスト成功だけを根拠にした低判定。

## レビューの深さとの連動

- 🟢 低: 定型チェック ＋ 人間の差分確認
- 🟡 中: code-reviewer ＋ 人間
- 🔴 高: code-reviewer ＋ Codex 第二意見 ＋ 該当分野の専門レビュー ＋ 人間（分野は security / data-migration / ui / test のフラグで別管理し、高だからといって全部に security を付けない）
  ＋ **人間が自分で再現・確認できる状態**（下）

最終 merge と本番・ストア・live 操作の実行判断は常に人間。

### 🔴 高で用意するもの（人間が自分で確かめる側の道具）

**🔴 高の PR ほど人間が自分で見たいのに、そこが一番準備が要る。** AI が実行したコマンドと結果を並べるだけでは、人間は同じことを再現できない。次の 3 つを用意し、PR 本文の「確認方法と結果」の「自分で再現する」に書く。

| 用意するもの | 決まり |
|---|---|
| 再現に要るデータを**作るスクリプト** | 「手元に偶然あったファイル」に依存させない。**本体の定数・スキーマを書き写さない**（本体を通す。写すと本体だけ増えたときに黙って古い状態を作り続ける）。**作ったものが本当に問題の状態かをスクリプトの中で確かめる**（確かめずに出すと、状態の作り損ねを「直っている」と読み違える） |
| 修正前・修正後を**比べる手順** | `git worktree` で 2 つの版を並べる。`git stash` で修正だけ戻す形は、ビルドを 2 つ並べられないので使わない |
| 実機・エミュレータが要るときの**準備と片付け** | 要る理由（なぜ机の上で足りないか）、ビルドの種類、ファイルの置き方、終わったあとの消し方。**机の上だけで確かめられる経路を先に書く**（多くはそこで足りる） |

置き場所はこのリポジトリの `tool/repro/`（リポジトリに慣例があればそれに従う）。出力は `.gitignore` 済みのディレクトリに出し、**成果物をリポジトリに入れない**。通常のテスト実行（`flutter test` や `npm test` の引数なし）の対象に入れない。
