# Revia の要件（MVP）

実装の根拠にする文書。**なぜ作るか**は [concept.md](concept.md)、**リスクの判定基準**は [pr-risk-policy.md](pr-risk-policy.md)。

## MVP の範囲

**「話せる間道」に絞る**（2026-09-23 の判断）。教材を 1 冊登録して、状態を記録して、復習一覧で見直すまでの**一本道**を先に通す。

```
目次を撮影 → AI が解析 → ユーザーが確認・修正 → 登録
                                                  ↓
                          復習一覧で見直す ← 状態を変える
```

| 機能 | MVP | 備考 |
|---|---|---|
| 教材一覧 | ✅ | |
| 教材追加（目次の複数枚撮影） | ✅ | |
| AI による目次解析 | ✅ | 方式は Issue #6 で実測して決める |
| 解析結果の確認・修正 | ✅ | **実質ツリー編集 UI。MVP で一番重い** |
| 問題番号の範囲一括生成 | ✅ | これが無いと問題の階層を作れない |
| 教材詳細（ツリー表示） | ✅ | |
| 状態のクイック変更 | ✅ | タップで循環。詳細画面を開かせない |
| 復習一覧 | ✅ | ここでも状態を変えられる |
| 手動での教材登録 | ⏭ 後回し | **ツリー編集 UI ができれば「空から始める」だけ**。逃げ道は失われない |
| メモ | ⏭ 後回し | データモデルには列を持っておく |
| 進捗表示 | ⏭ 後回し | ただし教材一覧の集計は必要（下の「集計は葉だけを数える」） |
| クラウド同期 | ⏭ 後回し | **作る方向**（ポートフォリオとして見せる対象）。ただし MVP は一本道を通すのが目的なので入れない。**後から外せる作りにする**（[concept.md](concept.md)「現在の位置づけ」） |
| 課金（Play Billing） | ⏭ 後回し | Play へ公開すると決めたときだけ。AI の従量課金を補填する。**🔴 高** |
| AI チャット | ❌ | |
| 問題画像の保存 | ❌ | |
| AI による学習指示 | ❌ | 思想に反する |
| 塾向けの管理 | ❌ | |

## 画面

### ① 教材一覧

登録した教材を並べる。教材ごとに集計を出す。

```
Revia

基本情報技術者        学習済み 32 / 要復習 12
TOEIC 文法            学習済み 78 / 要復習 23
数学III               学習済み 21 / 要復習  8

                            ＋ 教材追加
```

### ② 教材詳細（最も重要な画面）

階層をツリーで表示し、**状態の部分をタップするだけで変えられる**。詳細画面を開いて保存する操作にはしない。

```
基本情報技術者

▼ 第1章 コンピュータ
   ✓ 1.1 CPU
   🔁 1.2 メモリ
   ✓ 1.3 ストレージ

▼ 第2章 ネットワーク
   ✓ 2.1 TCP/IP
   🔁 2.2 HTTP
       ○ 問題1
       🔁 問題2
       ✓ 問題3
       ○ 問題4
```

### ③ 復習一覧

`要復習` が付いたものだけを、教材・章ごとにまとめて出す。**ここでも状態を変えられる。**

```
要復習

基本情報技術者
  第1章    🔁 1.2 メモリ
  第2章    🔁 2.2 HTTP
             ├ 問題2
             └ 問題7

TOEIC 文法
  🔁 問題32
  🔁 問題41
```

### ナビゲーション

Bottom Navigation は `📚 教材` と `🔁 復習` の 2 つ。設定などは別の導線にする。

## 状態モデル

**「結果」と「復習」はデータ上で分けて持つ**（2026-09-23 の判断）。

| 列 | 値 | 意味 |
|---|---|---|
| `result` | `unstarted` / `correct` / `wrong` | やったか、合っていたか |
| `needs_review` | 真偽 | もう一度やりたいか |

**この 2 つは本来別の概念。**

- 間違えたが、解説を読んで完全に理解した → `wrong` だが `needs_review` は false
- 正解したが、自信がなかった → `correct` でも `needs_review` は true

### MVP の UI は 1 タップのまま

データは分けるが、**MVP の画面では 3 つの状態を循環させるだけ**にする。操作量を増やさないため。

| 表示 | `result` | `needs_review` |
|---|---|---|
| `○` 未着手 | `unstarted` | false |
| `✓` 完了 | `correct` | false |
| `🔁` 要復習 | `wrong` | true |

タップで `○ → ✓ → 🔁 → ○` と循環する。

**分けて持つ理由は、後から「結果」と「復習」を独立に操作する UI を足すときに、データの移行が要らないから。** 1 つの列で始めると移行が必要になり、それは `pr-risk-policy.md` で 🔴 高に当たる領域（版を戻してから上げ直す経路で DB が開けなくなる事故が他のリポジトリで実際に起きている）。

## データモデル

**階層は可変ツリーで持つ**（2026-09-23 の判断）。教材によって `章→節→問題` `章→問題` `章→節→小節→問題` と段数が違うため、固定の段数にしない。

```
materials
  id            TEXT    PRIMARY KEY
  title         TEXT    NOT NULL
  created_at    INTEGER NOT NULL
  updated_at    INTEGER NOT NULL

items
  id            TEXT    PRIMARY KEY
  material_id   TEXT    NOT NULL  → materials.id
  parent_id     TEXT    NULL      → items.id（NULL なら最上位）
  kind          TEXT    NOT NULL  chapter | section | question
  label         TEXT    NOT NULL  "第1章 コンピュータ" / "1.1 CPU" / "問題12"
  order_index   INTEGER NOT NULL  同じ parent の中での並び順
  number        INTEGER NULL      問題番号の数値。**MVP では書かない**（下の「問題番号」）
  result        TEXT    NOT NULL  unstarted | correct | wrong
  needs_review  INTEGER NOT NULL  0 | 1
  note          TEXT    NULL
  created_at    INTEGER NOT NULL
  updated_at    INTEGER NOT NULL
```

- **`kind` を持つ理由**: 階層は `parent_id` だけで表せるが、問題だけは範囲一括生成の対象になり、表示も変わるため区別が要る
- **状態は全階層が持つ**: 節にも問題にも `✓` `🔁` が付く（画面 ② のとおり）
- **`note` と `number` は MVP では書き込まないが列は持っておく**: 後から追加すると移行が要るため

### 集計は葉だけを数える（2026-09-23 の判断）

教材一覧の「学習済み 32 / 要復習 12」は、**葉（子を持たない項目）だけ**を数える。ユーザーが実際に登録した一番細かい単位になる。

```sql
-- 分母
SELECT COUNT(*) FROM items
WHERE material_id = ?
  AND id NOT IN (SELECT parent_id FROM items WHERE parent_id IS NOT NULL);
```

**分母の意味が教材ごとに変わることは受け入れる。** 問題まで登録した教材は問題数、節までの教材は節数になる。教材を並べて数字を比べる画面は作らないので、実害が出ない。

`kind = question` だけを数える案は、**問題を 1 つも登録していない教材が `0 / 0` になる**ので採らなかった。節単位で管理する使い方を殺してしまう。全項目を数える案は、**親に印を付けると子と二重に数えられる**ので採らなかった。

### 問題番号は文字列で持ち、`number` 列は用意だけする（2026-09-23 の判断）

教材によって番号の振られ方が違う（節ごとに 1 から / 巻末まで通し / `12-1` の枝番）。**どれか 1 つに決められない**ので、表示は `label` の文字列に任せる。

| 持ちもの | MVP での扱い |
|---|---|
| `label` | 表示に使う文字列（`"問題12"` `"12-1"`） |
| `order_index` | 並び順。**並べ替えはこれだけで足りる** |
| `number` | **列は持つが書かない。** 後から並べ替えや範囲指定に使うとき、移行を要らなくするため |

範囲一括生成の UI は「**接頭辞 ＋ 開始〜終了**」にする。

```
接頭辞 [問題]   [1] 〜 [30]
  → 問題1, 問題2, … 問題30 を order_index つきで生成
```

**枝番（`12-1`）は生成では作れない。** ツリー編集で手で足す。MVP の範囲では、枝番を持つ教材は手作業が増えるが、登録できないわけではない。

### 階層はデータ上は無制限、表示で打ち切る（2026-09-23 の判断）

`parent_id` に段数の制限を入れない。**深さの問題は表示の問題なので、表示で解く。**

| 層 | 扱い |
|---|---|
| データ（`items`） | **無制限。** 登録を拒否しない |
| 表示（教材詳細のツリー） | **4 段目以降は字下げを増やさない。** 画面幅を超えさせない |
| AI の解析結果 | **4 段に正規化してから確認画面に出す。** ユーザーが確認画面で直せる |

実際の教材はほぼ 4 段以内（`部 → 章 → 節 → 問題`、`章 → 節 → 小節 → 問題`）。

**データ側で 5 段目を拒否する案は採らなかった。** AI が 5 段の目次を返したときに「どの段を潰すか」の判断が要り、間違えると目次の構造が壊れる。**データは落とさず、表示と正規化で吸収する**ほうが戻せる。

### 未決: 目次が複数ページにまたがるとき

複数枚の写真を撮る前提だが、**ページをまたいだ章の連続性**をどう扱うか。

- 写真を撮った順に解析して単純に連結するか
- ページごとに解析してから統合するか
- 重複や欠落をユーザーに見せて直させるか

## 実装で気をつけること

- **移行（マイグレーション）の列追加は冪等に書く。** 他のリポジトリで「版を戻してから上げ直した端末で DB が開けなくなる」事故が起きている（`AGENTS.md` §6）
- **デモとテストに実在の教材の目次を使わない。** 自作の架空の目次を使う（公開リポジトリ）
- **AI の解析結果は必ずユーザーの確認を通す。** 自動で登録を確定しない（思想）
